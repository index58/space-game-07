# Реализация UI Kit

Используй этот скилл для любых изменений игрового UI проекта. Цель скилла: не давать UI расползаться на локальные копии разметки, CSS и hit-test логики.

## Главное Правило

Любое визуальное изменение интерактивного UI Kit-элемента считается незавершенным, пока его hit-test область не проверена и, если нужно, не обновлена.

Если визуально элемент занимает всю строку, ячейку, шкалу или расширенную область, область попадания игрового курсора должна совпадать с этой видимой интерактивной областью, а не только с внутренним DOM-узлом.

## Источники Проекта

Перед правкой UI найди общий источник для нужного типа элемента:

- Базовые контролы: `client/src/ui-kit/components.tsx`
- Стили базовых контролов: `.ui-kit-*` правила в `client/src/style.css`
- Геометрия hit-test: `client/src/ui-kit/hitRect.ts`
- Сбор DOM-контролов: `client/src/game/GameScene.ts`
- Runtime поведения UI: `client/src/ui-kit/runtime.ts`
- Общий каркас игровых модальных окон: `.game-window-layer` и общие modal-правила

Не создавай локальную замену для уже существующего типа контрола. Если текущему общему компоненту не хватает возможности, расширь его через props, children или modifier-класс, а затем используй это общее расширение в конкретном окне.

## Порядок Работы

1. Определи тип UI-элемента.

   Реши, относится ли изменение к существующему общему типу: окно, кнопка, вкладка, выпадающий список, поле ввода, edit-поле, чекбокс, слайдер, scrollbar, список, tooltip, контекстное меню, подпись строки или строка формы.

2. Найди существующий общий шаблон.

   Перед правкой прочитай соответствующий компонент и CSS. Также найди другие использования этого же элемента в окнах чата, настроек и панели управления.

3. Классифицируй изменение.

   Разделяй эти поверхности:

   - Только данные или текст
   - API общего JSX-компонента
   - Общий CSS-стиль
   - Геометрия: ширина, высота, padding, gap, overflow, wrapper, transform
   - Интерактивность: click, drag, selection, input, scroll
   - Hit-test: прямоугольник, зарегистрированный для игрового курсора

4. Сначала меняй общий источник.

   Если элемент относится к существующему UI Kit типу, делай переиспользуемую правку в `components.tsx`, `.ui-kit-*` CSS или общем helper. Локальные классы используй только для размещения в конкретном месте, а не для дублирования базового вида или поведения контрола.

5. Синхронизируй hit-test при изменении геометрии.

   Если правка влияет на видимый размер, форму, padding, width, height, overflow, структуру wrapper или видимую область клика/drag:

   - Проверь `client/src/ui-kit/hitRect.ts`.
   - Проверь `collectGameUiControls()` в `client/src/game/GameScene.ts`.
   - Убедись, что зарегистрированный rect совпадает с видимой интерактивной областью.
   - Для drag-контролов убедись, что `controlRect`, который используют обработчики, совпадает с той же областью, по которой считаются fill/position.

6. Держи поведение и визуал на одной системе координат.

   Для слайдеров, progress-bar-подобных контролов, scrollbars и draggable-контролов формула перевода позиции указателя в значение должна использовать те же min/max и rect, что и формула перевода значения в визуальное заполнение. Если заполнение показывает `current / total`, обработка мыши тоже должна считать значение от этой же доли.

7. Добавь тесты вместе с правкой.

   Выбирай тесты по риску:

   - API компонента или разметка: `client/src/ui-kit/components.test.tsx`
   - Общий CSS: `client/src/ui/style.test.ts`
   - Геометрия hit-test: `client/src/ui-kit/hitRect.test.ts`
   - Runtime click/drag: `client/src/ui-kit/runtime.test.ts` или тест соответствующего чистого helper
   - Конкретное окно и его композиция: `client/src/ui/GameUi.test.tsx`

   Для каждого нового общего UI-правила или новой общей возможности UI-элемента добавляй тест, который доказывает, что используется общий шаблон, а не локальная копия.

8. Проверяй без запуска приложения.

   Если пользователь явно не попросил запустить клиент или сервер, не запускай их. Предпочитай:

   ```powershell
   npm.cmd test
   npm.cmd run build
   ```

   Когда полезно, сначала запускай узкие тесты, затем полный набор клиентских тестов и сборку.

## Чеклист Hit-Test

Используй этот чеклист всякий раз, когда UI-элемент меняется визуально или интерактивно:

- Видимая область отличается от внутреннего DOM rect у `.ui-kit-control`?
- Элемент находится внутри ячейки строки, clipped viewport, dropdown menu или modal layer?
- Родительская ячейка визуально выглядит как область клика или drag?
- Элемент использует `transform`, внутренний сдвиг контента, overflow clipping или absolute overlay?
- Drag-обработчик использует `action.controlRect` для расчета значения?
- Зарегистрированный `controlRect` покрывает ту же область, которую пользователь видит как интерактивную?
- Есть тест на этот rect?

Если любой ответ указывает на возможное несовпадение, обнови `hitRect.ts` или логику сбора контролов и добавь сфокусированный unit-тест.

## Чеклист Размещения Контрола

Используй этот чеклист каждый раз, когда общий UI Kit контрол переносится в новый wrapper, строку, ячейку, колонку, нижнюю панель или другую область раскладки:

- Проверь не только сам общий компонент, но и новый родительский контейнер.
- Высота родителя должна быть явно совместима с высотой контрола: wrapper не должен незаметно растягивать, сжимать или сдвигать `.ui-kit-control`.
- У родителя должны быть осознанные `align-items`, `justify-content`, `line-height`, `padding`, `gap`, `min-height` и `box-sizing`.
- Если контрол должен выглядеть как в прежнем месте, сравни его с прежним использованием по высоте, вертикальному центру текста, padding и видимой рамке.
- Для кнопок текст должен оставаться геометрически по центру кнопки по вертикали и горизонтали; новый wrapper не должен менять визуальное положение надписи.
- Для полей ввода курсор и выделение текста должны оставаться в той же вертикальной системе координат, что и у других таких же полей.
- Для checkbox, slider и scrollbar проверь, что новый wrapper не меняет видимый центр, размер активной области и позицию внутреннего маркера/fill/thumb.
- Если меняешь контейнер вокруг `.ui-kit-control`, добавь CSS-тест на свойства контейнера и, когда это возможно, JSX-тест на то, что контрол находится именно в нужной области.

## Чеклист Слайдера

Для слайдеров и progress-like draggable-контролов:

- Слайдер должен быть расширением общего `Slider`, а не локальной разметкой.
- Формула визуального заполнения и формула pointer-to-value должны быть согласованы.
- Если нужен текст, добавь его как prop у `Slider` и стилизуй через `.ui-kit-slider__label`.
- Если визуальная шкала занимает всю ячейку значения формы, hit-test должен занимать ту же полную ячейку.
- Тесты должны покрывать fill width, текст, pointer mapping и hit-test rect, если это применимо.

## Чеклист Списка И Scrollbar

Для списков:

- Используй общий `ListBox` или расширь его.
- Фиксируй высоту элементов через общие стили списка.
- Сдвиг прокрутки клади в общий content списка, а не двигай отдельные элементы вручную.
- Если список обрезается viewport, элементы вне видимой области не должны регистрироваться кликабельными.
- Если scrollbar видим, используй общий `Scrollbar` и добавляй его состояние в UI control layout signature, когда это влияет на hit-test.

## Что Сообщать В Финале

В финальном ответе по UI Kit задаче укажи:

- Какой общий компонент, стиль или helper изменен.
- Проверялся или менялся ли hit-test.
- Какие тесты и команды сборки запускались.
- Если браузерная визуальная проверка не запускалась, скажи это прямо и укажи причину.
