## 🎯 1. Общее описание

### Цель
Создать клиент-серверную браузерную игру в жанре 2D space shooter с:
- Массовыми PvP-боями (до 1000 одновременных игроков)
- Бесшовным огромным миром (координаты `float64`, без зон загрузки)
- Низкой задержкой (<100 мс от ввода до отклика)
- Сложным реактивным интерфейсом (чат, инвентарь, дерево прокачки, статистика в реальном времени)

### Уже реализовано
- Браузерный клиент.
- Go-сервер.
- Полёт корабля.
- Камера.
- Звёздный фон.
- Серверная симуляция с тикрейтом 30 Гц.
- WebSocket-соединение для снимков мира и ввода игрока.
- Хранение данных в JSON-файлах.
- Периодическое сохранение изменённых данных сервером.
- Автоматическое создание стартового аккаунта, персонажа и корабля.
- Загрузка справочников клиентом перед подключением к игровому потоку.
- Отладочный оверлей с координатами, скоростью, углом поворота и FPS.
- Панель основных показателей посещаемого объекта.
- Отображение доступных клиенту кораблей, станций и астероидов.
- SolidJS UI-слой в отдельном DOM-контейнере поверх Phaser canvas.

### Ещё не реализовано
- WebTransport;
- protobuf-протокол;
- пользовательская регистрация и экран выбора аккаунта;
- инвентарь;
- бой;
- добыча;
- строительство.

Расчёт характеристик корабля выполняется сервером по данным модели и сборки.
Камера должна строго держать корабль в центре нижней половины экрана носом вверх.
Для управления направлением корабля используется Pointer Lock.
Отладочный оверлей показывается всегда.
Весь пользовательский интерфейс клиента реализуется на SolidJS в отдельном DOM-контейнере поверх Phaser canvas.
Системный указатель мыши в игровых режимах не разблокируется: HUD, меню, инвентарь, настройки, чат, модальные окна, экран станции и другие игровые интерфейсы должны управляться игровым курсором и игровым вводом, а не браузерными DOM-событиями мыши.
DOM-слой игрового UI является слоем отображения и не должен перехватывать мышь; кликабельность игрового UI реализуется через игровую модель наведения и активации.

### Визуал

#### Мир
*Фон космоса* — шейдер с бесконечным замощением одной текстурой, содержащей чёрный фон со звёздами
Масштаб текстуры звёздного фона: `2` точки на метр.
*Космические объекты*
- Корабли, станции, астероиды, лут — готовые текстуры
- Летящие снаряды, ракеты, лучи, поля — пока непонятно, как лучше сделать

Готовые текстуры игрового мира кладутся в следующие каталоги:
- `client/public/assets/world/backgrounds/` — текстуры звёздного фона
- `client/public/assets/world/cosmic-objects/ships/` — текстуры кораблей
- `client/public/assets/world/cosmic-objects/stations/` — текстуры станций
- `client/public/assets/world/cosmic-objects/asteroids/` — текстуры астероидов
- `client/public/assets/world/cosmic-objects/loot/` — текстуры лута

Файлы ассетов должны подключаться через стабильные ключи в манифесте ассетов, а не напрямую через имена файлов в игровой логике.
Все PNG-текстуры кораблей должны быть нарисованы носом вверх при нулевом угле поворота.
Отладочная отрисовка серверных физических многоугольников включается и выключается клавишей `O`.
Клиент рисует физические многоугольники голубым полупрозрачным слоем поверх космических объектов.
Отладочная панель показывает путь к файлу текстуры объекта, на котором находится текущий персонаж.

#### UI
*Иконки объектов и предметов* — готовые текстуры
*Панельки, кнопки, списки, переключатели, и весь остальной UI* — пока непонятно, как лучше сделать

Иконки объектов и предметов кладутся в каталог `client/public/assets/ui/icons/`.
Для иконок, у которых ещё нет финальных ассетов, можно использовать временные заглушки.
Для текстур космических объектов временные заглушки не используются.
Визуальный стиль UI должен быть предложен при проектировании UI.

## 🧱 3. Архитектура системы

### 3.1. Общая схема
Симуляция игрового состояния выполняется на сервере и должна быть отделена от рендера Phaser: симуляция хранит координаты, скорости, углы, силы и игровые правила, а Phaser отвечает за отображение, камеру, фон, загрузку ассетов и обработку низкоуровневого ввода.

Целевая клиент-серверная схема:
```
[Браузер: Клиент]
  ├── Ядро игры: TypeScript + Phaser 4 (WebGL 2.0)
  ├── UI-слой: SolidJS (реактивный, отдельный DOM-контейнер)
  ├── Сеть: WebTransport (web-transport-web) + WebSocket fallback
  ├── Сериализация: protobuf (ts-proto)
  └── Синхронизация: интерполяция + клиентское предсказание

[Сервер: Go]
  ├── Транспорт: quic-go (WebTransport/HTTP3) + gorilla/websocket (fallback)
  ├── Протокол: protobuf (google.golang.org/protobuf)
  ├── Пространство: spatial hash (фиксированная сетка)
  ├── Параллелизм: worker pool
  ├── Тик-лук: фазы Input → Simulate → Barrier → Apply → Broadcast
  ├── AOI: Area of Interest router (рассылка только видимого)
  └── Мониторинг: pprof + Prometheus metrics

[Контракт]
  └── Единый файл: shared/game.proto → генерация кода для Go и TS
```

### 3.2. Данные и хранение
Целевая база данных — PostgreSQL.
До перехода на PostgreSQL прогресс будет сохраняться в JSON-файлы по правилу: одна таблица = один JSON-файл.
Во время работы сервера данные в памяти должны иметь такую же структуру: одна таблица = один `map` с ключом `ID`.
Целевой формат имени JSON-файла таблицы: имя сущности в PascalCase без расширения в логике и с расширением `.json` в файловой системе.
Пример: таблица `CosmicObjectModel` хранится в файле `shared/data/CosmicObjectModel.json`.
При сохранении таблиц в JSON поле `Items` записывается в порядке возрастания числовых `ID`, чтобы результат сохранения был детерминированным.
На Linux имена файлов чувствительны к регистру, поэтому в коде и документации нужно использовать точное совпадение регистра.
Чтобы разработка на Windows не скрывала ошибки регистра, доступ к таким файлам должен идти через единый список констант или манифест, а не через произвольные строковые литералы.

Данные из таблиц, хранящихся в JSON-файлах, не должны храниться в клиентском коде, клиентских константах или клиентских сборочных артефактах как источник игровых справочников.
Клиент должен получать такие данные динамически с сервера.
Относительно постоянные таблицы-справочники клиент должен загружать сразу при входе, до начала использования игрового мира и связанных с ними моделей:
- `NpcClan`
- `CosmicObjectType`
- `Itemtype`
- `CosmicObjectModel`
- `ItemModel`
- `Blueprint`
- `BlueprintComponent`
- `Schema`
- `SchemaComponent`

Сервер загружает мир и справочники из локальных JSON-файлов и периодически сохраняет изменённые данные.
Справочные данные нужны: из них берутся параметры кораблей и других моделей.
Характеристики управляемого корабля выбираются на основе модели космического объекта и публичной сборки разработчика.
Стартовый корабль: `ship_bat` (`Летучая мышь`).
Тестовый неподвижный астероид: `asteroid_0002`, координаты `X=-500`, `Y=800`.
Тестовая неподвижная станция: `station_tiny_crumb`, координаты `X=500`, `Y=500`.

При переносе старого файла `shared/data/cosmic_object_models.json` в актуальную структуру используется следующий маппинг полей:
- `TextureObjectOriginX` -> `TextureBodyOriginX`
- `TextureObjectOriginY` -> `TextureBodyOriginY`
- `TextureObjectWidth` -> `TextureBodyWidth`
- `TextureObjectLength` -> `TextureBodyLength`
- `TextureObjectArea` не переносится
- `CosmicObjectType` позже заменяется на `CosmicObjectTypeID`

Старый файл `shared/data/cosmic_object_models.json` остается как есть.
Новый файл с актуальной структурой создается отдельно с новым именем `shared/data/CosmicObjectModel.json`.
Если в старых данных у модели объекта нет поля `TextureScale`, используется значение `4.0`.
Поля `ThrustForce` и `Torque` из старого JSON держатся во временной конфигурации совместимости и не добавляются в актуальную модель данных.
Для приведения старых данных кораблей к физическим единицам массы всех кораблей умножаются на `1000`, а силы тяги всех кораблей умножаются на `200000000`.
После такого масштабирования у `ship_bat` масса равна `7920` кг, сила тяги равна примерно `1287902` Н, ускорение равно примерно `162.61` м/с².
Ускорение кораблей из старого файла после масштабирования находится примерно в диапазоне от `94.60` до `162.61` м/с².
Для временной конфигурации совместимости `Torque` из старого JSON умножается на `1000`.
Момент инерции рассчитывается как для заполненного эллипса по физическому телу объекта: `I = Mass * (BodyWidth^2 + BodyLength^2) / 16`.
При загрузке `CosmicObjectModel` сервер рассчитывает поле `BodyPolygon`.
`BodyPolygon` содержит 16 локальных точек физического тела в метрах и не сохраняется в JSON.
Точки строятся по эллипсу, вписанному в прямоугольник `TextureBodyWidth / TextureScale` на `TextureBodyLength / TextureScale`.
Центр локального физического тела смещается по `TextureBodyOriginX`, `TextureBodyOriginY` относительно центра текстуры с учетом `TextureScale`.

## 📐 4. Пространственная модель и оптимизация

### 4.1. Углы

**Все углы в проекте — только в радианах**
**Все углы в проекте — непрерывные (без нормализации)**

- Сервер хранит и отправляет углы в радианах
- Клиент получает углы в радианах
- Физика, коллизии, интерполяция — всё в радианах
- Никаких градусов в коде, протоколе или конфигах
- Нулевой угол поворота корабля — нос корабля смотрит в направлении роста оси Y
- Положительное направление поворота — по часовой стрелке

| Где | Единица | Диапазон |
|-----|---------|----------|
| Сервер (Go) | радианы | `float64` |
| Сеть (proto) | радианы | `float64` |
| Клиент (TS) | радианы | `float64` |
| Рендер (Phaser) | радианы | Phaser сам обработает |

### 4.2. Система координат

**Сервер и клиент используют разные направления оси Y.**

| Где | Направление Y | Направление X |
|-----|---------------|---------------|
| Сервер (игровой мир) | **вверх** (+Y = север) | вправо |
| Клиент (Phaser 4.0.0) | **вниз** (+Y = юг, экран) | вправо |

При рендере серверные координаты преобразуются в экранные:

```ts
phaserWorldX = worldX
phaserWorldY = -worldY
```

Если камера не повернута, точка мира переводится в точку экрана так:

```ts
screenX = (worldX - cameraWorldX) * zoom + viewportWidth / 2
screenY = -(worldY - cameraWorldY) * zoom + viewportHeight / 2
```

Для камеры пилота корабль должен оставаться носом вверх экрана.
Для этого мир или камера поворачиваются на `-shipRotation` относительно пилотируемого корабля.
Диапазон масштаба камеры: от `0.01` до `100`.
Начальный масштаб камеры равен `4`.
Масштаб камеры меняется колесом мыши.

Максимальная скорость корабля пока не ограничивается значением `MaxSpeed`.

### 4.3. Серверная физика движения и столкновений

Серверный шаг симуляции сначала обновляет движение всех `Enabled` объектов без `Anchored`, затем разрешает столкновения всех пар объектов в стабильном порядке возрастания `ID`.
Корабль считается пилотируемым только если его `ID` есть среди значений `world.accountObjectIDs`: аккаунт подключен, а текущий персонаж аккаунта находится на этом корабле.
Пилотируемые корабли обрабатываются вводом пилота и штатным автоторможением от двигателей.
Корабли без подключенного пилота используют свободный шаг с автоматическим линейным торможением `MaxAlongForce / Mass` против текущей скорости и угловым торможением `1 рад/с^2` против текущей угловой скорости.
Свободное торможение не меняет знак скорости: если за тик торможение больше текущей линейной или угловой скорости, соответствующая скорость становится `0`.
Объекты без подключенного пилота, которые не являются кораблями, используют свободный шаг без корабельного торможения.

Для столкновений сервер использует SAT по выпуклым `BodyPolygon` двух объектов.
Результат SAT: факт пересечения, нормаль столкновения и минимальный вектор выталкивания.
Точка контакта рассчитывается как центр области пересечения двух многоугольников.
Если область пересечения выродилась, точка контакта рассчитывается через опорные точки по нормали столкновения.

Импульс столкновения применяется в точке контакта.
В расчете используются `Mass`, обратная масса, момент инерции, обратный момент инерции, линейная скорость и угловая скорость каждого объекта в точке контакта.
Коэффициент реституции столкновений равен `0.5`.
Момент инерции рассчитывается по формуле `I = Mass * (BodyWidth^2 + BodyLength^2) / 16`.
Для `Anchored`, `!Enabled` и объектов с некорректной массой обратная масса и обратный момент инерции считаются равными `0`.
Некорректной массой считается масса, которая меньше или равна `0`.

Если угловой импульс добавляет кораблю изменение угловой скорости `deltaω`, сервер сдвигает `TargetRotation` на `sign(deltaω) * deltaω^2 / (2 * angularAcceleration)`.
Этот сдвиг сохраняет новый целевой угол после физического отскока и не дает управлению возвращать корабль к старому углу.

### 4.4. Spatial Hash (сервер)
```go
// КОНТРАКТ: функция должна быть детерминированной и без аллокаций в горячем цикле
func CellKey(x, y, cellSize float64) (int, int) {
    return int(math.Floor(x / cellSize)), int(math.Floor(y / cellSize))
}
```

**Параметры:**
- `cell_size = 1500` (единиц мира) — рассчитано как `1.5 × max_weapon_range (1000)`
- Проверка взаимодействий: **3×3 соседние клетки** всегда покрывают дальность оружия
- Пустые клетки не хранятся в памяти (`map[CellKey]*Cell`)

AOI пока не ограничивает видимость.
Клиент считает доступной бесконечную область мира.

## Единый игровой UI Kit

Весь новый игровой UI должен реализовываться в едином стиле на основе клиентского UI Kit.
Новые панели, модальные окна, меню, кнопки, галочки, списки, выпадающие списки, вкладки, полосы прокрутки, слайдеры, числовые поля, поля горячих клавиш, разделители, drag-and-drop и текстовые поля нельзя делать как локальные самописные DOM/HUD-решения, если в UI Kit уже есть подходящий primitive.
Все полосы прокрутки игрового UI должны переиспользовать единый primitive UI Kit `Scrollbar`: списки, выпадающие списки, чат, настройки и будущие панели не должны использовать нативные браузерные полосы прокрутки или локально нарисованные варианты, если нет отдельного архитектурного решения пользователя.

Кодовые точки UI Kit:
- `client/src/ui-kit/types.ts` — публичные типы контролов, действий и состояния текстового редактора.
- `client/src/ui-kit/runtime.ts` — registry контролов, hit-test, focus, hover, pressed и drag-capture для игрового курсора.
- `client/src/ui-kit/textEdit.ts` — скрытый native `textarea` как общий движок текстового ввода, выделения, буфера, раскладок и IME.
- `client/src/ui-kit/components.tsx` — визуальные SolidJS primitives единого HUD-стиля.
- `client/src/style.css` — CSS-правила `.ui-kit-*` и общий визуальный стиль контролов.
- `client/src/ui/GameUi.tsx` — подключение UI Kit к игровому HUD и отладочная showcase-панель.
- `client/src/game/InputController.ts` — маршрутизация игрового курсора, клавиатуры и мыши в UI Kit без DOM pointer events.

DOM-слой игрового UI остаётся слоем отображения: `pointer-events` для игрового UI не включаются. Взаимодействие с UI должно идти через игровой курсор, общий UI runtime и игровой ввод. Исключения допускаются только после отдельного изменения архитектуры пользователем.
