# Go WebSocket Authoritative Physics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first Go backend that owns ship physics, accepts player input over JSON WebSocket, and broadcasts authoritative world snapshots to the Phaser client.

**Architecture:** The server is authoritative and keeps all world state in memory. The client sends input 30 times per second, renders the latest full snapshot, and does not run local ship physics.

**Tech Stack:** Go 1.22+, `github.com/gorilla/websocket`, TypeScript, Vite, Phaser, Vitest, Go tests.

---

## Fixed Decisions

- Server protocol: JSON over WebSocket.
- WebSocket URL: `ws://127.0.0.1:8080/ws`.
- Server tick rate: 30 Hz.
- Client input send rate: 30 Hz.
- State storage: memory only.
- Multiple simultaneous players are supported.
- One `ship_bat` is created per WebSocket connection.
- A disconnected player's ship is removed immediately.
- New player spawn point is random inside a 500 meter radius from world center `(0, 0)`.
- Server broadcasts a full snapshot after each simulation tick.
- Snapshot contains all player ships plus static `asteroid_0002` and `station_tiny_crumb`.
- World object IDs are numeric. Model acronyms remain separate strings.
- Server physics must match current `client/src/domain/physics.ts` behavior, including `maxSpeedMps`, `targetRotation`, independent local-axis braking, and continuous angles.
- Client without server connection shows waiting status and does not request Pointer Lock.
- Do not start the client or server unless the user explicitly asks. Verification commands may build and test only.

## JSON Protocol

### Client To Server: Input

```json
{
  "type": "input",
  "seq": 42,
  "thrustForward": true,
  "thrustBackward": false,
  "thrustLeft": false,
  "thrustRight": false,
  "targetRotationDelta": 0.0125
}
```

### Server To Client: Snapshot

```json
{
  "type": "snapshot",
  "tick": 123,
  "selfObjectId": 1,
  "objects": [
    {
      "id": 1,
      "modelAcronym": "ship_bat",
      "kind": "ship",
      "x": 10.5,
      "y": -3.2,
      "velocityX": 1.1,
      "velocityY": 0.4,
      "rotation": 0.2,
      "angularVelocity": 0.01,

      "id": 2,

      "y": 800,
      "velocityX": 0,
      "velocityY": 0,
      "rotation": 0,
      "angularVelocity": 0,
      "targetRotation": 0
    }
  ]
}
```

## Task 3: Port Physics To Go

**Files:**
- Create: `server/internal/physics/physics.go`
- Create: `server/internal/physics/physics_test.go`

- [ ] **Step 1: Implement physics helpers**

Create functions equivalent to current TypeScript helpers:
- `BodySizeMeters(model game.CosmicObjectModel)`;
- `MomentOfInertia(ship game.WorldObject)`;
- `ForwardVector(rotation float64)`;
- `RightVector(rotation float64)`;
- local `brakeValue`;
- local `clampVectorLength`;
- local `clampAbsoluteValue`;
- local projection helper.

- [ ] **Step 2: Implement ship physics step**

Create:

```go
func StepShip(ship game.WorldObject, input game.ShipInput, dtSeconds float64) game.WorldObject
```

Behavior must match current `stepShipPhysics`:
- local forward/right axes are derived from current rotation;
- forward/back and left/right thrust affect separate local velocity projections;
- no input on an axis causes braking on that axis;
- `targetRotation` is incremented by `input.TargetRotationDelta`;
- angular velocity accelerates toward target and brakes before overshoot;
- linear velocity is clamped by `ship.Model.MaxSpeedMps`;
- angular velocity is clamped by `ship.Model.MaxAngularSpeedRadPerSecond`;
- rotation and target rotation are not normalized.

- [ ] **Step 3: Add physics parity tests**

Create Go tests matching current TypeScript expected values:
- moment of inertia equals about `490173.75`;
- 1 second forward thrust gives velocity Y about `162.61382953137096`;
- 10 seconds forward thrust clamps speed to about `497`;
- input target delta updates target rotation;
- angular velocity starts toward target rotation;
- angle error across `-pi/pi` is not normalized;
- angular speed clamps to `3`;
- idle input brakes linear and angular speed;
- longitudinal thrust still brakes transverse velocity;
- transverse thrust still brakes longitudinal velocity;
- simultaneous `W+S` does not brake longitudinal axis;
- simultaneous `A+D` does not brake transverse axis.

- Modify: `client/src/game/DebugOverlay.ts`
- Modify: `client/src/domain/types.ts`

- creating local `ShipState` through `createInitialShipState`;
- calling `stepShipPhysics`;
- mutating ship state from local input.

`GameScene` must keep:
- Phaser asset loading;
- input collection;
- camera transform;
- sprite rendering.

- [ ] **Step 2: Add network client lifecycle**

In `create()`:
- instantiate `GameClient`;
- instantiate `InputController` with connected-state gate;
- keep static asset setup.

In `update()`:
- get current input and pass it to `GameClient`;
- get latest snapshot;
- if no connected snapshot, render waiting status and skip Pointer Lock-dependent gameplay rendering;
- if snapshot exists, find `selfObjectId`, use it as pilot camera anchor, render all objects.

- [ ] **Step 3: Render dynamic players and static objects**

Maintain a map of object ID to Phaser image.

For each snapshot:
- create missing sprites based on `modelAcronym`;
- update position, rotation, and scale;
- remove sprites that no longer exist in the latest snapshot.

The self ship must render nose-up as before. Other objects use `rotationToPilotScreen`.

- [ ] **Step 4: Update debug overlay**

Overlay must show:
- connection status;
- self object ID when present;
- position;
- speed;
- rotation;
- angular velocity;
- zoom;
- FPS.

When waiting for server, overlay or centered text must show that connection is pending.
